## 2. In-Depth Connection Setup & Code Walkthrough

### A. Jira Service Management (JSM)
* **Code Location**: `backend/services/support-service/src/integrations/jiraClient.ts`
* **How Connection is Created**:
  ```typescript
  // Lines 24-49 in jiraClient.ts
  const authHeader = 'Basic ' + Buffer.from(`${userEmail}:${apiToken}`).toString('base64');
  const response = await fetch(`${baseUrl}/rest/api/3/issue`, {
    method: 'POST',
    headers: {
      'Authorization': authHeader,
      'Content-Type': 'application/json',
      'Accept': 'application/json',
    },
    body: JSON.stringify({
      fields: {
        project: { key: projectKey },
        summary: `[${payload.category}] ${payload.summary}`,
        issuetype: { name: 'Service Request' },
        labels: ['HealthShield', payload.category]
      }
    })
  });
  ```
* **Dual-Mode Fallback**: If `JIRA_BASE_URL` or `JIRA_API_TOKEN` are not set, the code automatically executes lines 53-57, generating a simulated ticket key (e.g. `HS-1042`), meaning the application **never crashes** during local development or when credentials are not yet supplied.

---

### B. Splunk HTTP Event Collector (HEC)
* **Code Location**: `backend/services/support-service/src/integrations/splunkLogger.ts`
* **How Connection is Created**:
  ```typescript
  // Lines 42-53 in splunkLogger.ts
  await fetch(hecUrl, {
    method: 'POST',
    headers: {
      'Authorization': `Splunk ${hecToken}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(logPayload),
  });
  ```
* **Dual-Mode / OpenShift Native Logging**: In line 38, every audit event is also printed as structured JSON to `stdout`. When deployed on OpenShift, the OpenShift Cluster Logging Operator (Vector/Fluentd) automatically forwards this stdout stream to Splunk without needing custom sidecars.

---

### C. Kafka & AWS S3 Sink Connector
* **Event Publisher**: `backend/services/billing-service/src/events/kafkaPublisher.ts`
* **Connector Manifest**: `gitops/openshift/kafka/03-kafka-s3-sink-connector.yml`
* **How Events Flow to S3**:
  1. Microservice emits a payment event to topic `payment.events`.
  2. Kafka Connect runs the `io.confluent.connect.s3.S3SinkConnector` plugin.
  3. The connector flushes events in batches of 1,000 or every 5MB into AWS S3 bucket `healthshield-kafka-events-794558722040`.
  4. Authentication uses `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` provided via OpenShift Secret.

---

### D. AWS S3 Healthcare Document Vault
* **Code Location**: `backend/services/document-service/src/routes/documents.ts`
* **Security Pattern**:
  - Medical documents are never stored in unencrypted plain text.
  - Every document uploaded computes a **SHA-256 integrity hash** (`crypto.createHash('sha256')`).
  - Pre-signed S3 URLs enforce time-limited upload permissions.
  - Files are encrypted at rest using AWS S3 SSE-AES256.

## 3. Configuring OpenShift Secrets

Before deploying to OpenShift, create the secret using `gitops/openshift/secrets-template.yml`:

```bash
oc apply -f gitops/openshift/secrets-template.yml
```

Or inject via command line:
```bash
oc create secret generic healthshield-secrets \
  --namespace=health-insurance \
  --from-literal=DB_PASSWORD=postgres123 \
  --from-literal=JWT_SECRET=health-insurance-secret-key-2026 \
  --from-literal=AWS_S3_KAFKA_BUCKET=healthshield-kafka-events-794558722040 \
  --from-literal=AWS_S3_DOCUMENTS_BUCKET=healthshield-documents-794558722040 \
  --from-literal=AWS_ACCESS_KEY_ID=YOUR_AWS_ACCESS_KEY \
  --from-literal=AWS_SECRET_ACCESS_KEY=YOUR_AWS_SECRET_KEY \
  --from-literal=JIRA_BASE_URL=https://your-domain.atlassian.net \
  --from-literal=JIRA_USER_EMAIL=admin@yourcompany.com \
  --from-literal=JIRA_API_TOKEN=YOUR_ATLASSIAN_TOKEN \
  --from-literal=JIRA_PROJECT_KEY=HS \
  --from-literal=SPLUNK_HEC_URL=https://your-splunk-host:8088/services/collector \
  --from-literal=SPLUNK_HEC_TOKEN=YOUR_SPLUNK_HEC_TOKEN
```
